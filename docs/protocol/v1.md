# OpenSMS device protocol v1

Contract between the Android app (`opensms`, public) and the backend (`opensmsapi`, private). The copy in the `opensms` repo (`docs/protocol/v1.md`) is canonical once the app exists; keep both copies identical. Reference implementation: `src/protocol/messages.ts`, `src/durable/DeviceSession.ts`, `src/services/jobs.ts`.

All times are Unix milliseconds unless a field says ISO-8601. All JSON.

## 1. Identity and login (REST)

The app identifies itself with a **static device ID** (`Settings.Secure.ANDROID_ID`). The server stores only an HMAC of it. After a factory reset, or with a different app signing key, the ID changes and the phone is a new device.

### `POST /v1/devices/login` (every app launch)

```json
{
  "static_id": "9774d56d682e549c",
  "name": "My SMS Gateway",
  "device": { "model": "Pixel 8", "manufacturer": "Google", "os_version": "15", "app_version": "0.1.0", "timezone": "Asia/Kolkata" },
  "terms": { "version": "2026-10-01", "accepted_at": "2026-10-17T08:00:00Z" }
}
```

* With a valid `Authorization: Bearer <device_secret>` → **200** `{ "status": "approved", "device": <summary> }`. The summary contains `settings` (+ `revision`), `sims`, `callback`, `usage_today`, `websocket_url`.
* Without a secret (new install or reinstall) → **202**
  ```json
  { "status": "pending", "request_id": "req_…", "claim_token": "osc_…", "kind": "new|reinstall", "poll_after_seconds": 15, "expires_at": "…" }
  ```
  The app keeps `request_id` + `claim_token` (encrypted) and polls `/v1/devices/claim`. The old secret (if any) stays valid until the admin approves **and** the app claims.
* **403** `device_banned` – the app must show a blocked screen and stop. **403** `registration_closed`. **429** rate limited.

### `POST /v1/devices/claim`

`{ "request_id": "req_…", "claim_token": "osc_…" }`

| Result | Meaning |
| --- | --- |
| 202 `pending` | keep polling (not faster than every 5 s; use `poll_after_seconds`) |
| 200 `approved` | `{ device_id, device_secret: "osd_…", device: <summary> }` – **the secret is shown once**; store it encrypted (Android Keystore). Any older secret and socket are revoked. |
| 403 `install_rejected` | admin rejected; the user may try again later |
| 410 `request_expired` | expired / replaced by a newer request / already claimed → log in again |
| 403 `device_banned` | blocked |

If the claim response is lost, log in again (a new approval is needed).

## 2. WebSocket (`wss://<host>/v1/connect`)

* Upgrade request: `Authorization: Bearer <device_secret>` (never in the URL). 401 `credential_revoked` → log in again. 403 `device_banned`.
* One connection per device; a new one closes the old with code **4001**.
* Text frames only, one JSON object per frame, `"type"` is mandatory. Unknown/invalid messages get `{"type":"error","code":"invalid_message",…}` (connection stays open); non-JSON or binary frames close the socket with **4005**.
* Keepalive: use WebSocket **ping frames** (OkHttp `pingInterval(30s)`) – answered by Cloudflare without waking the server object. The text frame `ping` is answered with `pong` the same way.
* The server closes with these codes:

| Code | Name | App behaviour |
| --- | --- | --- |
| 4001 | replaced | another connection took over; do not reconnect immediately |
| 4002 | credential_revoked | log in again (needs approval) |
| 4003 | device_banned | stop; show the blocked screen |
| 4004 | unsupported_protocol | update the app |
| 4005 | protocol_error | fix client; reconnect with backoff |
| 4006 | heartbeat_timeout | reconnect |
| 4007 | terminated_by_admin | reconnect with backoff |

### 2.1 Handshake and reconciliation

1. App → `device.hello`
   ```json
   { "type": "device.hello", "protocol_version": 1, "app_version": "0.1.0",
     "device": { "model": "Pixel 8", "manufacturer": "Google", "os_version": "15" },
     "timezone": "Asia/Kolkata",
     "sims": [ { "slot": 1, "present": true, "carrier_name": "Jio", "display_name": "Jio", "country_iso": "IN" },
               { "slot": 2, "present": false } ],
     "settings_revision": 4, "last_acked_event_id": "01J…",
     "in_flight": [ { "job_id": "job_…", "attempt_id": "att-…", "state": "submitting" } ] }
   ```
   `in_flight` = **every job the phone has persisted whose final result the server has not acknowledged**, including jobs whose result events are still unacked.
2. Server → `device.ready`
   ```json
   { "type": "device.ready", "server_time": 1760000000000, "session_id": "ses_…", "heartbeat_interval_seconds": 60,
     "settings": { "revision": 4, "settings": { … }, "effective_daily_limit": 100 },
     "reconcile": { "redispatch": ["job_…"], "lost": ["job_…"] } }
   ```
   Reconciliation rules the server applies at `hello`:
   * job `dispatched` but not in `in_flight` → returned to `queued` and re-sent later (`redispatch`) – safe, the phone never accepted it;
   * job `accepted`/`submitting` but not in `in_flight` → marked `unknown` (`lost`), **never re-sent**.
3. App uploads unacked events (`events.batch`, ≤ 100 per frame); the server answers `events.ack`.
4. App → `{ "type": "device.accepting" }`. **Only now** does the server send `sms.command`s.

### 2.2 Messages: app → server

| type | fields |
| --- | --- |
| `device.heartbeat` | `sims?` (same shape as hello), `queue_depth?` – send every `heartbeat_interval_seconds`; the server closes the socket (4006) after 3 missed intervals (180 s default) |
| `device.settings.ack` | `revision` |
| `events.batch` | `events: [ <sms event>, … ]` |
| `sms.accepted`, `sms.submitting`, `sms.sent`, `sms.delivered`, `sms.failed`, `sms.unknown` | see below |

SMS event (also valid inside `events.batch`):

```json
{ "type": "sms.sent", "event_id": "01J8Z0Q5M2K3T7X9A1B2C3D4E5", "job_id": "job_…", "attempt_id": "att-…",
  "ts": 1760000000123, "sim": 1, "segments_total": 2, "segments_sent": 2,
  "error_code": "…", "error_message": "…", "stage": "send" }
```

* `event_id`: unique, phone-generated (ULID/UUID, 10–64 chars `[A-Za-z0-9_-]`). Processing is idempotent on it.
* `attempt_id`: unique per attempt (also the key of the `PendingIntent` callbacks).
* `sim`: 1 or 2 (the slot). `stage` (only `sms.failed`): `send` (default) or `delivery` (message was sent but the carrier reported non-delivery → status `undelivered`).
* The phone sends a single `sms.failed` for a job only after all of its own attempts (e.g. alternative SIM) are exhausted, and `sms.unknown` for ambiguous outcomes (e.g. only some multipart parts were sent → `error_code: "partial_send"`).
* The server acknowledges only **after the event is committed**: `{"type":"events.ack","event_ids":["…"]}`. Keep events locally until acked; re-send unacked events after reconnecting.

### 2.3 Messages: server → app

`sms.command`
```json
{ "type": "sms.command", "job_id": "job_…", "to": "+919876543210", "text": "…", "sim": "auto|sim_1|sim_2",
  "expires_at": 1760000600000, "segments_estimated": 1, "encoding": "gsm7|ucs2" }
```
* Persist the job in the local database, **then** send `sms.accepted`. The same command may arrive twice (reconnect): dedupe by `job_id`.
* After `expires_at` the phone must refuse the job (`sms.failed`, `error_code: "expired"`).
* Re-check destination/recipient/limits locally; the server already did.

`device.settings` – pushed when the admin changes limits: `{ revision, settings, effective_daily_limit }`; reply with `device.settings.ack`.

`error` – `{ code, message, ref_type?, issues? }`.

### 2.4 Job states

`queued → dispatched → accepted → submitting → sent → delivered`; other terminal states: `failed` (confirmed not sent), `undelivered`, `unknown` (ambiguous, never auto-resent), `expired` (never accepted before `expires_at`). A late `sent`/`delivered` can still resolve an `unknown` job.

Server-side timers: queued/dispatched jobs expire at `expires_at` (+30 s grace for `dispatched`); `accepted`/`submitting` without a result for 15 min (default) become `unknown`.

## 3. Settings object (`PUT /v1/devices/me/settings`)

```json
{ "revision": 4,
  "settings": {
    "home_country": "IN",
    "destination": { "mode": "single|multiple|all", "countries": ["IN"] },
    "sims": { "sim_1": { "enabled": true, "daily_limit": null }, "sim_2": { "enabled": true, "daily_limit": 100 } },
    "sim_strategy": "preferred|round_robin|least_used", "preferred_sim": null,
    "retry_alternative_sim": true, "daily_limit": null, "pacing_interval_ms": 2000,
    "delivery_reports": false, "history_retention_days": 30 } }
```
`revision` must equal the stored revision (409 `revision_conflict` otherwise, with the current settings in `details`). The effective daily segment limit is the stricter of `daily_limit` and the admin cap; the phone must not exceed either, and per-SIM limits are enforced by the phone.

## 4. Recipient rules

1. Digits with an optional leading `+`; spaces, `-`, `.`, `(`, `)` are ignored; anything else → `invalid_recipient`.
2. Numbers without `+` are parsed as numbers of `home_country`.
3. The number must be *possible* for its country and have 10–15 digits in international format.
4. For `+91` the national number must be exactly 10 digits (`9876543210`, `919876543210`, `+919876543210`).
5. The calling code must belong to an allowed country (`destination`), otherwise `destination_not_supported`. Matching is by calling code (+1 covers the US and Canada).

Segments are estimated server-side (GSM-7 incl. extension table, else UCS-2; 160/153 and 70/67) with a maximum of 10 per message. The phone's real count (`segments_total`) is authoritative for usage.
